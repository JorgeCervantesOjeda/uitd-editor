================================================================================
GUÍA RÁPIDA DE AUTORÍA Y SEMÁNTICA UITDL PARA ESTUDIANTES (v3)
================================================================================

Para construir modelos en UITDL correctamente y sin errores de validación, es
necesario dominar los siguientes conceptos y reglas clave del lenguaje:

--------------------------------------------------------------------------------
1. SINTAXIS DE INCLUSIÓN Y ANIDAMIENTO (`[]` VS `()`)
--------------------------------------------------------------------------------
* En las cláusulas `DRAW`, la contención o anidamiento estructural se define
  estrictamente con corchetes `[]` (por ejemplo: `DRAW { 2[ 3[ 0 ] ] };`). Esto
  establece la relación de inclusión global en el modelo.
* En las sentencias `TRANSITION`, las referencias a instancias contenidas se
  expresan con paréntesis `()` (por ejemplo: `to 2( 3( 0 ) )`).

--------------------------------------------------------------------------------
2. SEMÁNTICA DEL ESTADO DE DESTINO EN TRANSICIONES
--------------------------------------------------------------------------------
* `to 2`: Envía al usuario a la UI contenedora (UI 2). En este estado, el
  usuario dispone de las acciones propias de la UI 2 más todas las acciones
  heredadas por inclusión de la UI 3 y la UI 0.
* `to 2( 3( 0 ) )`:
  - Anclaje visual de la casilla: La flecha del diagrama apunta y se ancla
    físicamente a la casilla o rectángulo de la UI más interna de la cadena
    (la UI 0, dibujada dentro de la UI 3 y esta dentro de la UI 2).
  - Estado subyacente activo: Aunque la referencia menciona las pantallas
    contenedoras (UI 2 y UI 3) para ubicar visualmente la casilla, el estado
    que se activa formalmente para la persona usuaria es EXCLUSIVAMENTE la UI 0,
    restringiendo las acciones disponibles únicamente a las definidas en la UI 0
    (sin activar las acciones de la UI 3 ni de la UI 2).

--------------------------------------------------------------------------------
3. REGLA DEL FRAGMENTO DEDICADO Y REUTILIZACIÓN DE MENÚS
--------------------------------------------------------------------------------
* Una UI reutilizable (como un menú de navegación presentable en 2 o más
  pantallas) debe ilustrarse de forma independiente (*standalone*) únicamente en
  su fragmento dedicado, mostrando sus transiciones de salida.
* En los demás fragmentos del sistema, la UI del menú se reutiliza mediante
  anidamiento (por ejemplo: `DRAW { 3[ 0 ] };`) para heredar sus acciones sin
  duplicar flechas de transición.

--------------------------------------------------------------------------------
4. CONECTIVIDAD Y COHERENCIA EN FRAGMENTOS
--------------------------------------------------------------------------------
* Cada fragmento debe ser un subgrafo conectado.
* Cada UI declarada dentro de un `DRAW` debe participar activamente en una
  transición (como origen o destino) o ser un nodo de inclusión necesario para
  interpretar ese fragmento. Queda prohibido incluir UIs aisladas o decorativas.

--------------------------------------------------------------------------------
5. VERBOS, GUARDS (`AND`) Y AUTO-BUCLES (*SELF-LOOPS*)
--------------------------------------------------------------------------------
* Verbos de interfaz vs. semánticos: Usa `clicks "etiqueta"` para controles
  visibles y verbos semánticos como `deletes "registro"` solo con objetos del
  dominio.
* Guards (`AND`): La proposición dentro de `AND "Condición"` debe ser una
  condición evaluable como verdadera ANTES de ejecutar la transición. No debe
  usarse para describir consecuencias ni efectos posteriores.
* Destinos explícitos: Reemplaza auto-bucles de marcador (`from 1 to 1`) por
  pantallas de destino explícitas (como una UI de error) cuando la acción
  represente un intento de avance en la navegación.

--------------------------------------------------------------------------------
6. ESPERAS TEMPORALES (`waits`) Y ESTADOS DE CARGA
--------------------------------------------------------------------------------
* `waits` representa que la persona usuaria permanece en la UI mientras se
  alcanza una finalización, un tiempo límite o una expiración observable.
  No representa el inicio interno de un proceso.
* Si una acción inicia una carga y aparece un modal bloqueante, modela el modal
  como una UI independiente. La acción inicial lleva a la UI de carga; después,
  una acción `waits` lleva a la UI cargada.
* Evita expresiones como `waits "data loading"`, porque describen el comienzo
  del proceso. Prefiere complementos de finalización como
  `waits "for the data to finish loading"`.

Ejemplo:

  UI 3 "Dashboard" actions { clicks "Account"; }
  UI 21 "Account Loading Modal" actions {
    waits "for the data to finish loading";
  }
  UI 22 "Account" actions {}

  TRANSITION from 3 to 21 if user clicks "Account";
  TRANSITION from 21 to 22 if user waits "for the data to finish loading";

--------------------------------------------------------------------------------
7. `WIDTH` ES SÓLO PRESENTACIÓN
--------------------------------------------------------------------------------
* `WIDTH n;` controla el ajuste de línea de las etiquetas y no modifica la
  semántica ni el comportamiento del modelo.
* `n` debe ser un entero positivo. El `WIDTH` del fragmento sirve como valor
  predeterminado para sus transiciones; un `WIDTH` de transición lo sustituye
  únicamente para esa transición.
* El ajuste debe contar caracteres, incluidos los espacios, y no dividir
  palabras.

--------------------------------------------------------------------------------
8. DETERMINISMO Y ACCIONES REPETIDAS
--------------------------------------------------------------------------------
* Si un control dinámico conserva la misma etiqueta visible, declara una sola
  acción con esa etiqueta. Expresa las alternativas mediante guards `AND` que
  sean mutuamente excluyentes y evaluables antes de la transición.
* No mezcles para una misma acción transiciones condicionadas y sin condición.
  Tampoco asignes varios destinos a la misma rama de acción y guard.
* Una acción declarada pero no usada en una transición no crea por sí sola un
  nodo visual; normalmente se reporta como advertencia.

--------------------------------------------------------------------------------
9. ALCANZABILIDAD E INCLUSIÓN JUSTIFICADA
--------------------------------------------------------------------------------
* Una UI operativa debe tener un camino lógico de entrada cuando el flujo lo
  requiera; evita estados huérfanos, como un panel administrativo sin acceso.
* Una UI incluida cuenta como reutilizable sólo si aparece en al menos dos UIs
  contenedoras distintas. Si aparece en una sola, justifica la relación como
  extensión o estado compuesto, no como reutilización.
* La inclusión debe justificarse por reutilización real o por una extensión
  semántica. No anides UIs sólo porque estén relacionadas temáticamente o para
  facilitar el dibujo.
* Una UI contenedora puede tener salidas efectivas heredadas de una UI incluida;
  revisa ese comportamiento antes de declararla incompleta.

--------------------------------------------------------------------------------
10. VALIDACIÓN Y LÍMITES DE LAS HERRAMIENTAS
--------------------------------------------------------------------------------
* En UITD Editor, los diagnósticos del panel textual son la fuente de bloqueo:
  los errores impiden aplicar el texto, previsualizarlo o generar D2; las
  advertencias siguen visibles y requieren revisión.
* Usa el validador del proyecto o los diagnósticos de UITD Editor. No pidas a
  estudiantes instalar paquetes externos sólo para validar un ejemplo.
* `Format` sólo normaliza espacios, sangría y estructura; no corrige errores
  semánticos.
* `Preview HTML`, D2, SVG y simulación de layout son artefactos operativos o
  de presentación. Que se generen correctamente no demuestra que el modelo
  sea semánticamente perfecto ni que la aplicación real esté implementada.
* UITDL no declara un estado inicial: la previsualización comienza en la
  primera UI declarada y permite elegir otra UI. Los guards tampoco se evalúan
  con el contexto real de una aplicación; la persona debe seleccionar la
  condición en la previsualización.
